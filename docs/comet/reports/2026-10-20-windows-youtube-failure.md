# Windows YouTube 实测失败取证

日期：2026-10-20；分支 `codex/windows-receiver`，起点 `34e78f2`，工作树初始干净。唯一目标是处理用户报告的“输入检测不合格，未取得恢复资格”。本轮没有改 Android、共享协议或 Mac，没有合并 main。

## 已确认的事实

用户说明测试播放器为 YouTube。本机旧日志显示：失败时 `healthy=true`；最后一次暂停请求的实际原因是媒体播放控件不可识别，旧界面却把媒体和输入错误合并成一条。更早的记录还有三秒进度不推进，以及一次发出暂停后输入代次变化。旧日志没有撤销类别，不能把后者直接归因于用户、自动化自身或钩子失效。

用户在 Chrome 手动播放后，使用项目已有 `--pilot` 和 `--probe` 取得 Windows 现场证据：同一前台窗口和文档、可调用 Pause 控件；进度核验期间 UIA 进度值持续不变，输入健康，前台与输入代次未变。补充只读数值探针后，独立时间文字和可见定位条也在连续采样中停留在相同秒值。隐藏的另一条定位值不同，但没有被选作产品时间线。

GSMTC 显示 Playing，其位置与更新时间是离散报告；不能把该位置按墙钟推算成真实媒体推进，也不能用推荐会话或进程名替代前台归属。此次未据它授予控制资格。

上述证据证明当前观察路径不能持续提供这个页面的进度，尚不能证明隐藏控件、某项 Chrome 设置或 Windows 权限是底层根因。问题属于观察数据的有效性契约：GUI 展示值存在且自洽，不等于它持续反映实际播放。Mac AX 的结果不能继承为 Windows UIA 的成立证据。

## 已实施与撤回

保留的改动：

- UIA 自有观察错误有明确类型，区分零候选和多个候选；界面分别显示输入监听失效、输入／连接撤销、媒体不可识别和未观察到实际进度。
- 输入钩子仅做原子分类计数，失败时输出摘要；区分键盘、鼠标、前台通知、外部撤销、心跳以及注入事件计数，不记录按键、坐标、窗口标题或页面内容。既有撤销规则没有放宽。
- 只读探针增加解析后的时间秒值、GSMTC 更新时间和速率；本机有界日志增加资格开始与输入摘要。没有原始 URL、令牌或图像。
- 诊断版为 0.1.1，启动日志从程序集读取版本，独立发布到 `.local/windows-diagnostics`；未覆盖旧运行目录或替换用户进程。

经独立审查后进行过本机有界焦点实验：仅已完整验证的目标、同文档非编辑焦点、执行前核验撤销代次／前台／健康／采样年龄；不发按键、不写定位值。播放按钮焦点没有恢复持续进度；定位条焦点未得到确认，按规则取消。属性事件订阅与原生 TextPattern 请求的只读实验仍未获得持续数值更新。**这些候选均没有成为功能修复，实验代码已清除。** 没有关闭进度检查、延长阈值或忽略来源不明的输入。

- `dotnet run --project apps/windows/PausePal.Windows.Tests -c Release --no-restore`：57/57，通过，包括媒体故障不误报输入、输入失效明确提示和进度冻结零操作；不是播放器通过。
- Release 构建：成功，零警告／零错误。诊断版单独 publish；命令输出和产物本机保留。
- `openspec validate windows-receiver --strict --no-interactive`：通过。
- `--ui-preview`：重新生成实际 WinForms 菜单与四态图标离屏图，已阅图，新状态文字无截断／重叠；不是系统托盘实景验收。
- 用户 YouTube 现场：仍失败，没有新的完整暂停／UNKNOWN／恢复成功证据。手机连接、B站、本地播放器及其他原 GAP 不因此关闭。
