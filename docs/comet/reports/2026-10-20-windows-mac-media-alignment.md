# Windows 媒体逻辑对齐 Mac 的实施记录

日期：2026-10-20。分支 `codex/windows-receiver`，起点 `2d63f21`，开始时工作树干净。用户在研究 Mac 实现、明确接管含义后授权“先按这个逻辑继续开发”。保持无扩展、不增加网页脚本权限；本轮没有改 Android、Mac 或共享协议。

## 问题与实现

此前用户 YouTube 现场的输入监听健康，UIA 时间值却持续冻结。Windows 实现把“明确播放状态”和“必须看到进度增长”同时设为暂停及恢复门槛；Mac 对明确状态不设统一进度门槛，只对模糊状态使用进度辅助。该契约差异使明确状态的路径也被进度阻断。底层 provider 为何冻结仍未确定，不能把本次逻辑迁移解释成底层数据新鲜度已经恢复。

本次实施：

- 明确 Playing 单次暂停后进入确认；同目标明确 Paused 且具有有效、未结束的位置锚点，才获得恢复资格。命令返回本身不算成功，确认超时不重试。
- 恢复前核验同目标、同时间来源和范围、原暂停位置、前台、输入代次与采样年龄；恢复命令后确认明确 Playing，不再强制实际进度增长。先消费资格，再最多尝试一次安全回退；回退前的新鲜读取也核验时间来源和范围。
- 目标身份与时间锚点分别比较。暂停前没有时间线、暂停后首次取得有效时间线可建立归属；暂停后仍缺失或时间源有歧义则取消资格，不自动播放。
- 时间只取精确媒体区域内唯一完整时间文字；没有时再读取唯一进度条的有单位时间描述。同一组合控件与子文字的相同值按祖先关系去重；独立相同数值、冲突数值仍拒绝。无单位数值不当作秒，不强制 slider 与 clock 双源一致。
- 手动键盘、点击、滚轮、换媒体或前台变化撤销本轮恢复资格，Watching 保持。用户手动继续播放，之后再次离开可以建立新轮，无需手机重新开始。自动暂停后只调音量也按接管处理；纯鼠标移动不取消。
- 保留 UNKNOWN 持有、初始手动暂停、结束、停止、断线和重连的原规则。没有加入音频判态、GSMTC 前台会话猜测、模糊按钮推断或通用远程输入接口。
- 新增固定字段的阶段观察诊断，缺失数值记录为 null，避免缺失时间线的 NaN 导致诊断序列化失败。没有记录原始 URL、网页文字、令牌或图像。

## 未闭合范围

真实 YouTube 状态转换和暂停锚点是否持续可读尚未证明。若播放状态也冻结，暂停确认应超时取消；若暂停锚点缺失，允许暂停但不得自动恢复。同步 UIA provider 调用只能返回后检查耗时，当前不能宣称具有可中断的硬时限；持有期仍使用完整读取，没有声称完成轻量观察优化。

同窗口／文档／控件／时长／暂停位置全部相同的换片，以及观察到执行之间的竞态仍属既有边界。旧 Windows Media Player 缺少可核验播放项身份仍不支持；不能把本次对齐说明为全播放器兼容。

手机接收协议、配对身份和四态托盘沿用前轮实现；本轮没有改变这些接口，也没有在 Windows 重签或覆盖 S25 应用。S25 发现、实际方向链、停止重连、普通托盘与登录启动，以及 B站／YouTube／本地多轮矩阵仍按[集中验收说明](../../../apps/windows/验收说明.md)执行。OpenSpec 的实施项 5.2 完成，真实效果项 5.3 及其他原 GAP 保留，不合 main、不归档活动变更。
